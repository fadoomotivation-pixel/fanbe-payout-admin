# Fanbe Payout CRM — complete guide for an AI coding assistant (Cursor / Claude)

Read this whole file before changing anything. This app moves real money (customer
payments, broker commission, payouts). A wrong line here pays a broker twice, shows a
customer a debt they do not owe, or lets a broker pay himself. Every rule below exists
because one of those things nearly happened.

---

## 1. What the business is

**Fanbe Group** sells residential **plots** in its own **projects** (colonies near
Vrindavan / Mathura / Faridabad etc.). Customers usually pay a **token**, then a
**booking deposit**, then the balance in monthly **EMI instalments ("kist")**, sometimes
with post-dated cheques (**PDC**). When fully paid, the sale deed is registered (**registry**).

Plots are sold through **brokers (agents)**. Two completely separate sales channels:

| | **MLM** | **Traditional** |
|---|---|---|
| Who | Network brokers, codes `FNB0xxxx` | Independent agents, codes `TRxxx` |
| Commission | % by the broker's **rank**, plus **differential** income to every upline | A fixed % (or ₹ per sq yd) agreed per booking; upline only if `traditional_pay_upline` |
| Tree | `sponsor_id` tree of MLM brokers | Separate tree of traditional brokers — never mixed |
| Booking flag | `bp_bookings.commission_mode = 'mlm'` | `commission_mode = 'traditional'` |

Commission is earned **per verified payment** — when the customer pays ₹1,00,000, the
brokers earn their % of ₹1,00,000 at that moment, not on the booking value.

### Apps sharing this code / database
- **Admin panel** — `admin.fanbegroup.com` (this repo, React + Vite, deployed on Vercel). Staff only.
- **Broker portal** — `/broker/login`, `/broker/dashboard` (same repo). A broker sees his team, his
  commission, asks for a withdrawal, uploads KYC. Broker login = broker code or phone; the default password is the broker's mobile number.
- **Collection app** — `/collect` (same repo, also packaged as an Android APK via Capacitor). Callers
  chase EMI dues, log calls.
- **Call-centre CRM** — a *different* app on the **same Supabase database** (tables `leads`, `calls`,
  `hr_*`, `attendance`, `site_visits`, `crm_*`, `employee_leads`, `profiles`). **Never modify or delete
  those tables from this repo.**

## 3. Domain glossary and data model

### Projects & plots
- `bp_projects` — a colony. `bp_plots` — one plot (`plot_no`, `size_sqyd`, `status`:
  `available | token | booked | registry_done`). Trigger `sync_plot_status` moves plot status with
  the booking stage. A plot must never be on two live bookings.

### Customer
- `bp_customers` — buyer (`customer_code` auto, `name`, `phone`, `pan`, nominee…). One customer can
  have several bookings. If a customer later becomes a broker, `brokers.customer_id` links them and
  the old code is kept in `previous_customer_code`.

### Booking
- `bp_bookings` — one sale. Key columns:
  - `stage`: `token_received | booking_done | cancelled` (only these three).
  - Value: `total_amount`, falling back to `plot_total_price` — **always use `bookingValue()`**.
  - `broker_id` (selling broker), `commission_mode` (`mlm`/`traditional`),
    `traditional_commission_pct` / `traditional_commission_per_sqyd` / `traditional_pay_upline`.
  - `plot_id` + `bp_booking_plots` (a booking can hold several plots), `project_id`, `size_sqyd`.
  - `legacy_booking_no` — number from the old paper register (set only by the importer).
  - registry: `registry_date`, `registry_doc_no`, `registry_completed_at`.
  - `booking_no` is generated by trigger `generate_booking_no` (customer-code based).
  - `bp_booking_brokers` — split commission between several traditional brokers.
  - `total_collected` / `balance_due` columns are **legacy, do not trust them**; compute from payments.

### Payment (receipt)
- `bp_payments` — every rupee received. `payment_type`: `token | booking | emi | full | full_payment`.
  `payment_mode`: `cash | neft | rtgs | imps | upi | cheque | dd`.
  `verification_status`: `pending | verified | rejected`. **Only `verified` is money.**
- `receipt_no` is assigned by trigger `bp_payments_set_receipt_no`. UTR uniqueness across tables is
  enforced by trigger `check_utr_unique_cross_tables` (client also checks via `lib/utr.ts`).
- Inserting / updating / deleting a payment fires **`payment_recompute_payouts`** → recomputes commission.

### EMI
- `emi_schedules` (one per booking, `status`: `active | closed | defaulted`) →
  `emi_installments` (`seq`, `due_date`, `amount`, `paid_amount`, `paid_at`, `status`, `payment_id`).
  There is **no `booking_id` on instalments** — join through `schedule_id`.
- The one rule for an instalment lives in `src/lib/emiStatus.ts`:
  paid = `status='paid'` OR nothing due; **overdue = due_date strictly before local (IST) today** and unpaid.
- Recording EMI money: `src/components/EmiPanel.tsx` → one `bp_payments` row (type `emi`) then the
  amount is allocated to the oldest open instalments.
- Old tables `bp_emi_schedule`, `bp_emi_installments`, `booking_emi_installments` are **dead**.

### PDC cheques
- `bp_pdc_cheques` — a cheque on file is **not** money. `pdc_clear_cheque()` creates the verified
  payment; `pdc_bounce_cheque()` deletes it (refused if its commission is already in a closed cycle).

### Old records (imported)
- ~800 bookings were imported from the old register with a price but **no payment history**.
  `isImported()` / `isPaidUnknown()` in `src/lib/bookingMath.ts`: an imported, priced booking with
  nothing recorded has an **unknown** paid amount — it must not be shown as "owes the full price",
  reminded on WhatsApp, or counted in "to collect". The pipeline bucket is `old_unrecorded`; staff
  enter one opening payment via "Enter paid till date".

### Broker
- `brokers` — `broker_id` (code, assigned by trigger `assign_broker_id`: `FNB0…` for MLM, `TR…` for
  traditional), `name`, `phone`, `broker_type` (`mlm`/`traditional`), **`sponsor_id`** (upline),
  `rank`, `rank_locked`, `status`, `kyc_status`, `tds_applicable`, bank details, `auth_user_id`
  (Supabase login), `customer_id`.
- `bp_broker_kyc` — KYC documents.

### Broker tree
- The tree is `brokers.sponsor_id` (parent). Rules enforced in the DB:
  - `enforce_same_type_sponsor` — an MLM broker's sponsor must be MLM, traditional under traditional.
  - `enforce_no_sponsor_cycle` — no loops.
  - `sync_tree_sponsor_with_booking_broker` — when a customer who is also a broker makes his first MLM
    booking, his tree sponsor follows that booking's broker.
- UI: `src/pages/BrokerTree.tsx`. `sponsor_tree` table exists but is empty; walk `sponsor_id`.

### Ranks (MLM)
- `commission_ranks` — slab table: Executive 5% → Senior Executive 5.5% → Sales Officer 6% →
  Senior Sales Officer 6.5% → Team Manager 7% → Senior Team Manager 7.5% → Assistant Sales Manager 8%
  → Sales Manager 8.5% → … → President 12% (`commission_pct`, `level`, qualification by team sq yd
  or by number of sub-ranks).
- `recompute_broker_ranks()` (DB, runs from a statement trigger on `bp_bookings`) promotes MLM brokers
  by team business; it only promotes, never demotes, and skips `rank_locked` brokers.

## 4. Commission — exactly how it is computed

**Single source of truth: the Postgres function `recompute_booking_payouts(booking_id)`.**
The client never inserts commission. (`lib/payoutEngine.ts` still contains old client-side
functions `distributePayment`, `computeDifferentialDistribution`, `distributeBookingCommission` —
they are **unused legacy; do not call them**. `distributePaymentCommission()` only *reads back*
what the trigger wrote.)

When it runs: trigger `payment_recompute_payouts` on every payment insert/update(amount,
status, booking)/delete; `trg_booking_broker_recompute` when a booking's broker changes;
`recompute_all_payouts()` manually.

What it does for one booking:
1. Delete that booking's `payout_distributions` rows **that are not in a payout cycle**
   (`cycle_id IS NULL`). Rows already in a closed cycle are money already paid — never touched.
2. For each **verified** payment with amount > 0 (and not already cycled), if the booking has a broker:
   - **Traditional with split brokers** (`bp_booking_brokers` rows): each broker gets
     `amount × their %` (`income_type = 'traditional_split'`). No upline.
   - **Traditional single broker**: direct % = `traditional_commission_pct`, or
     `per_sqyd × size_sqyd / value × 100`. Row `traditional_direct`. Upline only if `traditional_pay_upline`.
   - **MLM**: direct % = the selling broker's rank `commission_pct` (row `direct`). Then walk up
     `sponsor_id` (max 15 levels, stop at a type boundary): each upline earns the **differential**
     `their rank % − highest % below them` if positive (row `differential`).
3. Every row: `gross = amount × % `, `tds = gross × tds_pct`, `admin = gross × admin_charge_pct`,
   **`net_payout = gross − tds − admin`** (`app_settings.payout_config`: TDS 5%, admin 10%).
   **TDS and admin are deducted HERE, once.**

Imported old bookings are stamped `commission_mode='traditional', traditional_commission_pct=0`
so recording their old payments never pays commission again.

Table: `payout_distributions` (`booking_id`, `payment_id`, `beneficiary_broker_id`, `level`,
`income_type`, `gross_payout`, `tds_amount`, `admin_charge`, `net_payout`, `cycle_id`).

## 5. Payout — how brokers get paid

**Broker wallet** — `loadBrokerWallets()` in `src/lib/payoutEngine.ts` (used by Withdrawals,
Payout Cycles, Broker Sales; the broker portal mirrors it):
```
earned    = Σ payout_distributions.net_payout
paid      = withdrawals paid/closed + bp_payout_transactions paid      (net_amount)
pending   = withdrawals pending/approved + payout transactions pending/approved
advance   = expenses under the "Advance" head with broker_id            (isAdvanceHead)
available = max(0, earned − paid − pending − advance)
```
Two ways money leaves:
- **Withdrawal** (`withdrawal_requests`, page `Withdrawals.tsx`; broker can request from the portal):
  pays **exactly the requested amount** — `computeWithdrawal()` deducts nothing more, because
  `net_payout` is already after TDS/admin. (Deducting again was a bug — do not reintroduce it.)
- **Payout cycle** (`payout_cycles` + `bp_payout_transactions`, page `PayoutCycles.tsx`): batches all
  un-cycled distributions, stamps their `cycle_id`, and creates one transaction per broker **capped
  at the broker's wallet `available`** (so money already withdrawn is not paid twice, and an advance
  is recovered). Brokers with an open withdrawal are skipped.
- **Advances** are recorded on the Expenses page, head "Advance", broker selected.

Rules: a payment whose commission is in a closed cycle cannot be rejected, deleted or edited
(`assertPaymentNotCycled`); reopen the cycle first. Cancelling a booking reverses only un-cycled
commission and closes its EMI plan (`closeBookingMoney`).

Other programs: `AchieversClub.tsx`, `TeamRewards.tsx` (team reward tiers), `CommissionRanks.tsx`,
`PayoutTerms.tsx` (settings incl. maintenance mode).

## 7. Rules that must never be broken

1. **Money = verified payments only.** Use `sumVerified` / `paidByBooking`. Pending or a PDC cheque is not money.
2. **Commission only from the DB function.** Never insert/update `payout_distributions` from the client.
3. **TDS/admin are deducted once**, at commission credit. Withdrawals and cycles pay `net` as is.
4. **Never touch rows with `cycle_id`** (paid out). Guard with `assertPaymentNotCycled`.
5. **Cancelled bookings are not sales** and earn nothing; their EMI plan is closed.
6. **Old imported bookings with nothing recorded have an unknown balance** (`isPaidUnknown`).
7. **Dates are IST**: use `todayLocalISO()`, never `new Date().toISOString().slice(0,10)`.
8. **Never trust a single PostgREST call to return everything**: lists that can exceed 1,000 rows use
   `fetchAllRows`; `.in('id', bigList)` uses `inChunks`.
9. **One rule, one place**: do not re-implement value/balance/EMI/wallet maths in a page — import it.
10. **Downloads** go through `lib/download.ts` (mobile Chrome breaks otherwise).
11. **Security is RLS, not the UI.** Brokers log in as the same `authenticated` role as staff. Any new
    table that holds money needs staff-only write policies (`public.is_staff()`).
12. Don't delete or modify the call-centre CRM tables (§1).
13. UI copy is plain simple English; the office reads Hindi/English, so keep sentences short.

### Security status (important)
- `public.is_staff()` exists in the DB.
- Migrations **`20261003_lock_money_tables_to_staff.sql`** and **`20261004_money_integrity_guards.sql`
  are in the repo but NOT yet applied**. Until they are, any broker login can write to money tables
  through the REST API. Applying them is the first critical fix.

## 8. How to fix a critical bug safely (checklist)

1. Reproduce: find the exact page + function. Read the related lib in §6 first.
2. Check the DB side too: triggers on `bp_payments`, `bp_bookings`, `brokers`; functions
   `recompute_booking_payouts`, `recompute_broker_ranks`, `pdc_*`. Use `pg_get_functiondef` to read them.
3. Fix in the shared lib, not by patching one page. Keep the money rules in §7.
4. If the fix needs the DB, write a new migration file; never edit an applied one.
5. Run `npx tsc --noEmit -p .` (no new errors), `npm run check:globals`, `npm run build`.
6. Explain in the commit message what was wrong, who it affected, and how the fix proves itself.
